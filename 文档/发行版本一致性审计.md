# 发行版本一致性审计

> **问题**：GitHub 上其他人下载的版本，与我本机当前使用的版本，体验是否完全一致？
>
> **结论先说**：**不一致 —— 但责任不在代码，在「分发」这一步。**
>
> - 走 **clone / Download ZIP** 的人：与我本地**完全一致**（同一 commit、逐文件同内容、查看页实测行为相同）。
> - 走 **README 首推的「便携一体包」** 的人：**拿到的是一份落后约 2 天的旧版**，缺少最近的全部改动（微博仿站皮肤、气泡宽度修复、以及 3 个新启动器）。
>
> 一句话：**仓库是新的，Release 里的便携包是旧的。**
>
> 审计时间：2026-09-24 · 审计对象：`Tsingyun/bili-weibo-dm-backup` @ `0e6b83e`（183 个跟踪文件）

## 一、怎么取证的

不看"应该"，只看字节和实跑。四条线各留一份副本，逐文件 diff + 真实渲染：

| 代号 | 副本 | 怎么来的 | 等价于 |
|---|---|---|---|
| ① | 我的工作区 | 就是本机在用的目录 | 「我正在用的版本」 |
| ② | `_dlzip/` | `git -c core.autocrlf=false archive HEAD \| tar -x` | **GitHub 绿色 Download ZIP** |
| ③ | `_parity_fresh/` | `git archive HEAD \| tar -x`（本机 autocrlf=true） | `git clone`（Windows 默认配置） |
| ④ | `_parity_pkg2/dm-backup/` | `gh release download v0.1.0` 解包 | **便携一体包用户** |

②③④ 都跑了同一份 jsdom 探针（`_parity_probe/probe_viewer.mjs`），在**相同输入**（无数据）下比对渲染结果 —— 这样差异只可能来自代码本身。

| 维度 | 结论 | 说明 |

## 三、不一致清单（按严重度）

### 🔴 P0 · 便携包落后源码约 2 天（最主要的不一致）

**差异点（实测）**

- Release `v0.1.0` 发布于 **2026-09-22 05:10**；仓库最后推送 **2026-09-24 01:11**。
- 便携包共 **71 个条目 / 16 个启动器**（release notes 自述），当时回归基线是 `verify_webui 205/205`；现在是 **213/213**、**19 个启动器**。
- 与 HEAD 逐文件比对：**23 个同名文件内容不同**，其中包含核心文件：

  | 类别 | 具体 |
  |---|---|
  | 查看页 | `查看备份.html`、`webui/index.html`、`webui/app.js` |
  | 服务端 | `scripts/server.mjs`、`scripts/build_sessions.mjs`、`scripts/login.mjs`、`scripts/update.mjs`、`scripts/bili_update.mjs`、`scripts/doctor.mjs` 等 |
  | 文档 | `README.md`、`使用说明.md`、`文档/WebUI安全审计.md` |

- **仓库有、便携包没有**的 116 个文件里，用户能直接感知的是：

  - `命令/备份与更新/校验完整性.cmd`
  - `命令/备份与更新/漏抓对账.cmd`
  - `命令/查看与导出/高清截图.cmd`
  - `文档/仿微博聊天页-设计稿.html`
  - `文档/全项目隐私与合规安全审计.md`
  - `scripts/lib/jsassign.mjs`、`scripts/lib/runreport.mjs`、`scripts/requirements-ocr.txt`

- **三项最近的改动，便携包里一项都没有**（在 `查看备份.html` 里数出现次数）：

  | 标志物 | 便携包 | 我本地 |
  |---|---|---|
  | `width:fit-content`（短气泡宽度修复） | **0** | 4 |
  | `data-skin="weibo"`（微博仿站皮肤） | **0** | 25 |
  | `仿微博`（皮肤相关文案） | **0** | 5 |

- jsdom 实跑同一份查看页（同一无数据输入）：

  | 副本 | `html[data-skin]` | 页面可见文本 |
  |---|---|---|
  | ② Download ZIP 等价 | `weibo` | 155,155 字符 |
  | ① 我的工作区 | `weibo` | 155,155 字符 |
  | ④ 便携包 | **`null`** | **102,538 字符** |

  → 便携包的查看页**没有皮肤机制**，且功能文案少了 5.2 万字符。

**成因**

便携包是**构建产物**，不在 git 里，靠人工执行 `node scripts/pack_portable.mjs` 后手动上传 Release。README 里那个
`releases/latest/download/dm-backup-portable.zip` 链接写的「永远指向最新一版」只保证**指向最新 Release**，
并不保证**最新 Release 跟得上源码** —— 中间没有任何自动化。这次就是在两次发版之间改了 10 个文件、加了 3 个脚本，包没重打。

**调整办法**

1. **立刻重打并重新上传**（最小动作）：`node scripts/pack_portable.mjs` → 把新的 `dm-backup-portable.zip` 传成新 Release（或替换 `v0.1.0` 的资产）
2. **根因治理**：加一个 GitHub Action —— `push` tag 时自动跑 `pack_portable.mjs` 并上传资产，从此不可能再漂移
3. **加一句实话**：README 便携包那节补一句「便携包随 Release 更新；想看最新功能请用 clone」，避免用户以为两个入口永远同步

> 附带好处：重打会顺手把便携包里**那份未锁版本的旧 OCR 安装器**一起修好 ——
> 包里的 `安装OCR环境.cmd` 仍是 `pip install rapidocr onnxruntime pillow`（不锁版本），
> 也就是《全项目隐私与合规安全审计》M8 要修的那条供应链风险，在新代码里已经改成读 `scripts/requirements-ocr.txt` 锁版本了。
> 包内自洽（不会因为缺文件而崩），只是**旧**。

### 🟠 P1 · 行尾不确定：仓库全是 LF，却没有 `.gitattributes`

**差异点（实测）**

- `git ls-files --eol` 显示：**183 个文件在仓库里全部存 LF**（`i/lf` × 183，`i/crlf` 为 0），且仓库**没有 `.gitattributes`**。
- 于是两条官方下载路径拿到**不同的字节**：

  | 下载方式 | 得到的行尾 | 原因 |
  |---|---|---|
  | Download ZIP | **全 LF** | 服务端按仓库 blob 打包，无属性可依 |
  | `git clone` | **全 CRLF** | Git for Windows 安装默认 `core.autocrlf=true` |
  | 我本机工作区 | **混合**（161 LF / 21 CRLF / 1 mixed） | 我的 `core.autocrlf=true` + 部分文件被工具重写过 |

- **具体的风险面**：`命令/图片与OCR/安装OCR环境.cmd` 和 `卸载OCR环境.cmd` 里用了 `goto` 标签，
  而**只有 LF 行尾的批处理文件 + `goto` 在 Windows 上是已知的失败模式**（CMD 按字节偏移定位标签，LF 会算错）。
  这两个文件在仓库里存的正是 LF → **Download ZIP 的用户拿到 LF**。
  反过来，便携包里这两份是 **CRLF（安全）**，`git clone` 的也是 CRLF（安全）—— 只有 Download ZIP 这一路踩在线上。

**成因**

项目从未加 `.gitattributes`，把行尾完全交给使用者本机的 `core.autocrlf` 决定。

**调整办法**

加一个 `.gitattributes`，让所有下载路径产出**同一份字节**：

```gitattributes
* text=auto eol=lf
*.cmd  text eol=crlf
*.ps1  text eol=crlf
*.bat  text eol=crlf
```

加完需要跑一次 `git add --renormalize .` 让索引归一化，并复核 `git ls-files --eol` 不再出现 `w/mixed`。

**⚠️ 诚实标注**：本沙箱**禁止运行 `.cmd`**，所以「LF + goto 会不会真的失效」**我没有实测**，
上面是机制推断 + Windows 上的已知问题。加 `.gitattributes` 之后，**请人工双击一次 `安装OCR环境.cmd` 复核**。

### 🟡 P2 · 最低 Node 版本，三处口径不一致

**差异点**

| 出处 | 说法 |
|---|---|
| `README.md` / 便携包 `从这开始.txt` | `Node 22+` |
| `scripts/webui.ps1` 第 70 行（真正的门槛） | `if ($major -lt 18)` → 「需要 18 或更高」 |
| `scripts/build_fts.mjs` 注释 / `scripts/search.mjs` | `node:sqlite（Node ≥ 22）` |

**成因**

门槛是早期写的，那时只用到 `node:string_decoder` 与顶层 await 的 ESM（18 的确够）；
后来引入 `node:sqlite` 做全文检索，**没把门槛一起抬上去**。

**后果**

装了 Node 18 或 20 的用户：启动器**放行**、抓取和查看也都正常，
但一跑 `命令/查看与导出/重建搜索索引.cmd` 或 `搜索备份.cmd` 就会 `ERR_UNKNOWN_BUILTIN_MODULE` ——
**过了门槛才炸，且报错与"版本"看起来无关**，很难自查。

**调整办法**

1. 把 `webui.ps1` 门槛改成 `-lt 22`，提示里点名「搜索索引需要 Node 22」
2. 更稳的做法：门槛仍留在 18，但把 `node:sqlite` 改成**能力探测**（`try { await import('node:sqlite') } catch {}`），
   只在使用检索功能时给一句人话报错

### 🟡 P3 · `使用说明.md` 漏了「造 sessions.json」这一步

**差异点**

- `README.md` 第 2 步写得很清楚：`copy scripts\_skill\sessions.template.json sessions.json`
- `使用说明.md` **从头到尾没有这一步**，反而在目录树（第 790 行）把 `sessions.json` 当成**已经存在**的文件列出来。

**成因**

`使用说明.md` 是按「作者本机已有 `sessions.json`」写的；`README.md` 后补的 clone 路径没有回写进 `使用说明.md`，
两边从此没对齐。

**兜底（已实测有效，所以不是死路）**

1. **无 `sessions.json` 也能生成会话清单**：`loadSessions()` 在文件缺失时走 `FALLBACK_SESSIONS` 兜底
   （微博 + B站，dir 分别为 `data` / `bili`）→ 实跑 `node scripts/build_sessions.mjs` 输出
   `[✓] 已生成 sessions.js（2 个会话）`、exit 0。
2. **无 `sessions.js` 也能打开查看页**：`查看备份.html` 用 `onerror` 标记缺失并退回内置 `BUILTIN_SESSIONS`。
   ② 副本 jsdom 实跑：能打开、显示「尚无数据 / 未找到数据文件 <code>data/messages.js</code>」引导、**0 个 JS 错误**。
3. **真正要抓取时才要求配置**，且提示写得很好：抓取脚本调用 `peerUidOrExit()`，打印
   「还没有配置『要备份谁的私信』—— 这是第一次使用时的必填项」+「先从模板复制一份出来」+ 两条可直接照抄的命令，
   然后 **`exit 4` 干净退出**（不是抛异常糊一屏堆栈）。

→ 所以 README 第 4 步「双击 `查看备份.html`。就这样，没了。」**成立**。

**调整办法**

在 `使用说明.md` 补「第一次使用」小节（从模板复制 `sessions.json`），并把目录树那行标注成
「（首次由你从 `scripts/_skill/sessions.template.json` 创建）」。

## 四、已经一致的部分（避免误伤）

这些**都核对过，是对的**，不必动：

- ✅ **代码版本**：`git status` 干净，HEAD = 远端 = `0e6b83e08b4cdf4f81e4e13f00be3d96b0fba480`；183 个跟踪文件；Download ZIP 等价副本 = 同样 183 个文件。
- ✅ **查看页行为**：① 与 ② 在相同输入下渲染结果**逐项相同**（文本长度 155,155、`data-skin=weibo`、0 JS 错误、0 皮肤切换控件）。
- ✅ **零第三方依赖**：仓库里没有 `package.json`，不需要 `npm install`。
- ✅ **运行时版本**：便携包内置 `runtime/node/node.exe` = **v22.22.2**，与我本机沙箱 Node **完全一致**；且便携包的运行时优选逻辑（先看包内、再回退系统）是对的。
- ✅ **便携包内部自洽**：扫描包内全部 `.mjs/.js` 的相对 `import`，**没有一个指向包内不存在的文件**。它是「旧」，不是「坏」。

  黑名单本体 `personal_tokens.local.txt` **被正确排除**；包内 `sessions.json` 是空白模板（`peer.uid` 为空），`pack_portable.mjs` 还会断言 uid 为空。

- ✅ **仓库里没有个人数据**：抽查未发现本机绝对路径、真实 uid、口令。
