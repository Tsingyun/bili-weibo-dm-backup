# 「暂时无法校验 · 连不上平台接口」排查与修复

> 结论先说：**不是没登录，不是代理软件，是登录校验打的接口和抓取用的接口不是一个**。
> 已修好并推送（commit `6b08f79`）；两个平台现在都校验通过。

---

## 一、现象

Web UI 第 2 步一直显示「暂时无法校验 · 连不上平台接口」，但：

* 已确认不是「未登录」——浏览器里聊天页是登录状态；
* 不影响已存的数据；
* Clash 完全退出后依旧复现。

## 二、可能原因（按可能性排序）+ 逐个怎么验

| # | 原因 | 可能性 | 怎么验证（照抄就能跑） | 本机结果 |
|---|---|---|---|---|
| 1 | **校验接口地址/版本写错**（和抓取用的不是一个） | ★★★★★ | 拿同一份 Cookie 分别请求 `/chat/…` 与 `/webim/…`，比 status | **命中**：`/chat/`→502，`/webim/`→200 |
| 2 | 网络路径上的透明网关拦截特定路径 | ★★★★ | 看响应头 `server`（本机是 `SHANHAI-SERVER`）+ body 是不是 HTML | **命中**：502 页由该网关返回 |
| 3 | 残留代理环境变量（`HTTP_PROXY` 等） | ★★★ | `env \| grep -i proxy`；`unset` 后再请求 | 存在 `http_proxy=127.0.0.1:7471`，但清掉后**仍 502** → 干扰项不是主因 |
| 4 | 系统代理（IE/WinINET 代理开关） | ★★ | `netsh winhttp show proxy`、设置 → 代理；关掉再试 | 清 env 后仍失败，可排除为主因 |
| 5 | WAF / 风控返回 403 HTML 被当成"没登录" | ★★ | 看 body 是 JSON 还是 HTML | 已加固：非平台 JSON 一律判 `network` |
| 6 | DNS / hosts / IPv6 only | ★ | `nslookup api.weibo.com`、`type C:\Windows\System32\drivers\etc\hosts` | DNS 只返 IPv6，但同 host 的 `/chat/` 页面 200 → 排除 |
| 7 | 证书 / TLS | ★ | 换 `http://` 或换 UA 试 | 同一路径两种前缀都 502 → 排除 |
| 8 | 请求超时太短 | ★ | 把 timeout 拉到 30s 再试 | 502 是 58~140ms 立刻返回，不是超时 |
| 9 | 请求头缺 Referer / source 参数 | ★ | 补 `Referer: https://api.weibo.com/chat`、`source=209678993` 再试 | 已带齐仍 502 → 排除 |
| 10 | 离线降级逻辑本身有问题 | — | 看是不是把 `network` 当成 `expired` 拦截了 | `network` 早就是放行的，只是**提示语吓人** |

## 三、为什么「退出 Clash 后仍然失败」

三类东西不会因为退出代理软件而消失：

1. **残留的代理环境变量**：`HTTP_PROXY / HTTPS_PROXY / http_proxy / https_proxy`。
   Node 22 默认**不读**这些变量（要 `NODE_USE_ENV_PROXY=1` 才读），所以它对 Node 直连影响有限，
   但会影响 curl、pip、以及部分走 libcurl 的程序 —— 排查时容易被它误导。
2. **系统代理（WinINET / WinHTTP）**：和 Clash 是两回事，Clash 退出并不会自动清它。
3. **网络路径上的透明网关 / 中间盒**（本机这次就是这个）：它拦的是**特定 URL 路径**，
   与你本机装没装代理软件无关 —— 所以退出 Clash 当然没用。
   判据很硬：同一 host 上 `/chat/` 页面 200、`/webim/query_primary_info.json` 200，
   只有 `/chat/query_primary_info.json` 是 502，而 502 的响应头写着 `server: SHANHAI-SERVER`。

## 四、校验失败为什么不影响已存数据 / 能不能静默降级

* **不影响**：抓取脚本 `update.mjs` 直接读本地 `data/cookie_header.txt` 发请求，
  **根本不经过**登录校验这一步。校验只是界面上的一次"确认"，它的结论不参与抓取。
  已抓下来的消息、图片、OCR、索引都在 `data/` 里，不受任何影响。
* **已经在静默降级**：`network` 这条路径**不拦人**（只有 `expired` / `no-cookie` 才返回 401 拦住备份），
  界面文案也改成了「这不是'未登录'，已存的数据不受影响、备份照常能跑」。
  现在又多一层：浏览器通道被挡 → 自动回退直连其它端点 → 全都没结论才判 `network`。

## 五、已做的修复（commit 6b08f79）

1. `login.mjs` 的 `VERIFY` 改成**多端点**：主端点 = 抓取同款 `webim/query_primary_info.json`，
   旧 `chat/` 留作备用；表达式不再手抄 URL（新增 `pageFetchExpr()`）。
2. 分类收紧：5xx、或返回 HTML（网关 502 / WAF 403）一律 `network`；
   只有**平台自己的 JSON** 说"不认这个 Cookie"才是 `expired`。
3. 浏览器通道被挡时**回退直连**再试，不再直接判死；诊断里列出试过的端点。
4. 回归断言钉死「校验主端点 == `update.mjs` 的 `API_BASE` + 接口名」，以后改坏会立刻红。
5. Web UI 第 2 步新增**手动 Cookie** 兜底教程（见下）。

验证：

```
node scripts/login.mjs --session weibo --status   # → verified:true, account:"<你的微博昵称>"
node scripts/login.mjs --session bili  --status   # → verified:true, account:"<你的B站昵称>"
node scripts/_explore/verify_webui.mjs            # → 198/198
node scripts/_explore/verify_extras.mjs           # → 117/117
```

## 六、手动获取 Cookie（Web UI 第 2 步里也有，展开就能看到）

1. 用常用浏览器打开并登录：微博 `https://api.weibo.com/chat` · B站 `https://message.bilibili.com/`
2. `F12` → 顶部选 **Network / 网络**
3. `F5` 刷新，点**最上面那条**文档请求
4. 右侧 **Headers / 标头** → **Request Headers** 里的 `cookie: ...` → 右键 **Copy value**
5. 整串粘进 Web UI 第 2 步的框里（微博须含 `SUB=`，B站须含 `SESSDATA=`）→「保存并校验」

Cookie 等同于账号密码，只会写进本机 `<数据目录>/cookie_header.txt`，不外传、不上 Git。
