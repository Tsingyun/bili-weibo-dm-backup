2026-09-18 追加：「一天」的分界从 0 点改为凌晨 05:00

原来的「按天」是自然日 0 点切。问题是聊天常常一聊就到深夜， 一段「23:40 聊到 01:20」的对话会被劈成两天；而这份备份里凌晨那一段的量并不小：

P0 建议优先做 —— 投入小、收益直接

P0 1 · 图片转码压缩（WebP） 省 1.65~2.34 GB

价值本地占用直接砍到 1/3 ~ 1/20。你之前提过硬盘紧张，而图片就是唯一的体积大头（占 69%）。压完整套备份 ≈ 0.9 GB（A 档）或 0.2 GB（C 档），能塞进几乎所有免费云额度。 复杂度中。不只是转码：需同时迁移三处索引的文件名键 + 更新 messages.json 里的图片路径 + 重新跑一遍查看页回归。建议做成「一次性迁移脚本 + 更新链路里可选转码」两步。 实测见 §1.3，分层抽样转过真实数据，不是估算。 建议选 A 档（原尺寸 q82）先跑，肉眼无损；确定能接受再考虑 B/C 档。

P0 2 · 索引快照与回滚 防复现覆写事故

价值本项目真实发生过一次「边跑边写」把 174 条图片描述覆写成 59 条的事故。现在虽然加了单实例锁 + 读回合并，但锁挡不住逻辑写错、脚本改坏、误跑全量重建。有快照就能一键回退。 复杂度低。更新链路里加一步：把 messages/ocr/vlm/faces 打包（就 8 MB）存成带时间戳的 zip，保留最近 N 份。 建议强烈建议做。成本极低，但能兜住最贵的一类损失。

P0 3 · 一键体检 + 缺失图补齐 把散落的校验固定成命令

价值这次排查用到的检查（图片引用 vs 磁盘文件是否一一对应、有没有孤儿文件、索引覆盖率、锁文件是否残留、消息条数是否回退）目前都是临时写代码跑的。固化成 体检.cmd 后，每次更新完跑一下就知道有没有坏，并支持一键补下缺失的图。 复杂度低。逻辑都已经写过一遍了，只是收拢 + 输出成体检报告。 建议建议做。这是「数据可信」的兜底。

P0 4 · 定时自动更新（本机计划任务） 不再依赖记得双击

价值现在是「想起来才双击更新」。设成每天固定时间自动跑一次，备份就真的不会断更。你之前问过要不要加，这次可以一起做掉。 复杂度低。一条 schtasks 注册 + 一个静默版启动器（跑完自动关窗、日志落文件）。注意：我这边的沙箱不允许创建进程/计划任务，需要你双击一次注册脚本。 建议建议做。配合 P0-2 快照更稳。

P1 值得做 —— 中等投入，体验提升明显

P1 5 · 高级筛选

价值现在只有全文搜索。数据量到 2912 + 数千条后，很自然会想「只看我发的图片」「只看某个标签」「只看 2024 年下半年」「只看分享卡片」。加上发送者 / 类型 / 日期区间 / 正则四个维度会好用很多。 复杂度低~中。左侧面板加筛选组 + 在现有过滤函数里叠加条件，复用现有 DOM 重建机制。

P1 6 · 云端只读镜像（手机随时看）

价值现在只能在装了这个目录的电脑上看。把查看页 + 图片放到云端后，手机浏览器就能翻，也能分享给特定的人。 复杂度中~高。需配合云存储（见 §3）：图片上传 + 查看页改为指向远端 URL + 加访问控制。属于「要真的动手做工程」的一档。 风险隐私：私信是私密内容，一旦公开托管就等于公开。必须配访问控制（Cloudflare Access 免费版可指定邮箱白名单）。

P1 7 · 导出功能（按范围导出 / 加密分享包）

价值把某段时间的对话导出成 HTML / Markdown / TXT / JSON —— 既能长期存档（不依赖这个查看器），也能给别人一份、或喂给大模型。 复杂度中。渲染逻辑可复用；难点在图片要不要打包内联。

P1 8 · 日历热力图

价值已有「按天折线图」，但折线看不出一年的疏密。GitHub 那种方格热力图一眼就能看出哪段时间聊得密、哪天断档，也顺手能发现「哪几天根本没抓到」。 复杂度低。用已有按天统计直接渲染网格。

P1 9 · 多会话支持

价值当前聊天对象是写死在脚本里的（微博一个、B站一个）。如果想再备份第二个会话，现在得改代码。做成配置项后，加一行就能多备份一个对象。 复杂度中。数据目录要按会话分桶、查看页来源注册表要扩展。如果确定只备份这两个对象，可以不做。

P1 10 · 结构化导出给 LLM 用（JSONL）

价值把对话 + 图片 OCR 文字 + 图片描述 + 卡片标题摊平成一行一条的 JSONL。这样可以直接做语义检索、按主题归类、生成时间线摘要 —— 你做直播总结那套经验正好能复用。 复杂度低。纯数据加工，不需要动界面。

把已撤回的消息原文找回来做不到。撤回后服务端不再下发原文，本地从来没拿到过 —— 不是实现问题，是数据不存在。

3云端方案：存储 与 运行

先说一个关键前提 —— 我核实过代码：抓取脚本本身不需要浏览器。专用浏览器只用来「刷一次 Cookie」， 脚本会先读本地 cookie_header.txt，连不上浏览器时会打印「未连接浏览器，沿用本地 Cookie」继续跑。 也就是说 整条抓取链路本来就是可无头运行的，这正是它能上云的前提。

3.3 四种组合，按你的取向挑一个

组合 ① 零成本 + 隐私优先 最推荐

本机链路不变（继续用本地 CPU 跑 OCR）+ 每天自动更新 + 每周把压缩后的成品包（约 0.2~0.9 GB）自动传一份到 R2 或夸克网盘。

成本¥0 可靠性本地为主 + 云端一份异地副本，不怕硬盘坏 代价依赖电脑开机（可设成开机后补跑）

组合 ② 手机随时翻

图片压到 WebP 后放 R2（免费额度内），查看页托管到 Cloudflare Pages（无限带宽、无限请求），手机浏览器直接看。

成本¥0 可靠性高（Pages 全球 CDN） 代价要改造成「远端 URL 版」查看页；必须加访问控制

组合 ③ 完全无人值守

GitHub Actions 每天定时抓取 + OCR + 图片描述 → 图片推 R2 → 索引提交私有仓库 → Pages 自动发布。

成本¥0（2000 分钟额度远远够用） 可靠性高，不再依赖家里电脑 代价Cookie 需存 GitHub Secrets；需接受「凭据托管给第三方」

组合 ④ 花钱买省心

腾讯云轻量服务器跑完整链路 + COS 存图。境内网络对微博/B站最友好，不碰风控。

成本约 ¥60~200/年（促销价） 可靠性高 代价要维护服务器；COS 在线看图另有流量费
三条隐私红线，选任何云方案前请先确认：
  • 私信是私密对话，包含你和对方的所有往来。任何「公开链接」都等于公开。要上线就一定要设访问控制（Cloudflare Access 免费版可做邮箱白名单）。
  • bili/cookie_header.txt 与微博的 Cookie 等同账号密码。放进 GitHub Secrets 是可接受的工程做法，但你要清楚这意味着凭据交给了平台。
  • 国内网盘有内容审查与和谐风险。不要把唯一一份备份只放在某一个公有网盘里 —— 这是常识，不是技术问题。

4建议的下一步

如果要动手，我建议的顺序是：

  1. 先做 P0-2 快照回滚 + P0-3 一键体检（半天内能好，先给数据上保险）
  2. 再做 P0-4 定时自动更新（之后就不用惦记了）
  3. 然后做 P0-1 图片压缩（收益最大，但要迁移索引，放最后稳一点；建议先拿 100 张试跑验证索引迁移无误）
  4. P1 里挑你想要的（手机随时看 / 导出 / 高级筛选 价值最高）
  5. 云端先上组合 ①（零成本、隐私不动），确认用着顺再考虑组合 ③
